### Startup, state, UI and lifecycle

`App.xaml.cs` constructs a Generic Host with singleton services and transient windows/views, replaces logging providers with FileLoggerProvider, and configures an HttpClient with infinite transport timeout plus provider-scoped deadlines and redirects disabled. It loads settings, legacy credential migration, policy/activity/catalog/workspaces/projects; optional initialization failures are logged. Startup also starts Windows foreground/UIA events, native STOP hooks and optional developer adapters; catalog refresh runs in the background. These unconditional Windows paths prevent a Linux host from simply reusing App startup.

Navigation is shell code-behind selecting views, not a reusable navigation service. Full shell pages cover Home, Assistant, Applications, Workspaces, Projects, Developer, Permissions and Activity, with separate Settings/onboarding/editor/picker/inspection/diagnostic windows. MVVM infrastructure is small: ObservableObject/RelayCommand and character/settings ViewModels. Most complex views hold event wiring, controls, service calls and UI-state logic in code-behind. Reuse service behavior and presentation intent, not WPF controls.

The visual identity is the existing themed shell, floating vector companion, character states, compact interaction panel and notification bubble; asset state folders contain README placeholders rather than a complete sprite pipeline. Character priority combines own-task and developer-attention states. WindowService manages own windows/theme/position; external window authority is separate. WPF Dispatcher and event lifetimes must be replaced explicitly, with one shared conversation instance across full and compact chat.

Settings are mutable model snapshots with several tab-specific saves. Startup tasks, event callbacks, async-void UI handlers and local catches provide uneven failure isolation; not every native startup call is under InitializeSafelyAsync. Generic logging writes synchronous daily files, swallows logging failures, appends exception type/message, and has no implemented size/retention rotation. Do not claim ordinary logs are comprehensively secret-safe simply because AI-specific logs are redacted.

### AI, execution and permissions

`OpenAiCompatibleProvider` already implements configured model/base URL, scoped credentials, HTTP chat/completions SSE, model discovery and an inert forced-function connection test. It requires HTTPS or loopback HTTP, limits response text/tool payloads, requires valid call identity and stream completion, supports structured tools, and maps provider errors. It sends sequential-tool preference, bounded completions and per-request timeout; its strict streaming subset may reject some nominally compatible providers. It requires a credential even for keyless local endpoints. A retry on selected transient HTTP statuses can duplicate completion cost; desktop actions are not replayed by that HTTP retry. Provider text-delta support exists but the conversation call does not currently forward live deltas to the UI.

`AssistantConversationService` is the existing planner: one active human turn, deterministic-command fast path, otherwise bounded iterative model/tool calls. Ordinary requests have at most eight planning rounds/16 calls, at most four returned calls per round. Computer tasks have settings-controlled rounds/action limits and at most three calls per round. Calls execute sequentially through the exact-name AgentToolRegistry and ComputerAgentToolRouter. There is no separate general planner engine to introduce or replace.

Tool families are built from WindowsAgentTools, ProjectTools, ProjectFileTools, DeveloperTools, UiTools and ComputerActionTools. JSON schemas are accompanied by local validation, prepared target/capabilities, approvals and actual typed service execution. Router arguments are limited to 8,192 characters/depth eight, policy and target snapshots are checked around approvals, and execution deadlines are one minute (three for project/workspace launches). Direct AI commands use ComputerCommandService with source `AI`; they do not send text back through a model to execute a structured tool.

Conversation entries are bounded to 200 in memory; prior model protocol retains complete turns (up to ten / 32,000 aggregate characters). Context stores last app/workspace/tool/source and current project separately; source references are invalidated on project change. Retrieved file/developer/UI material is untrusted data, bounded/redacted, omitted from prior raw tool history and followed by restricted tool availability/execution checks. Assistant summaries may still retain derived information. Action replies use actual local outcomes. Regex-based grounding/task-completion rules are useful bounds, not proof that any arbitrary human goal was achieved.

`Stop()` cancels active turn/provider/tools, ComputerUseSession and UI inspection; workspace scheduling receives cancellation. It does not undo completed actions, interrupt every synchronous native call, or kill external developer agents. UIA has one bounded observation lane; a timeout does not forcibly terminate a hung in-process provider. Private Python child termination provides a harder worker boundary.

`JsonPolicyService` stores Allow/Ask/Deny; AgentCapabilities includes available and future/unavailable features. Preparation derives child permissions for composite actions. Approval service presents cancellable local allow-once/deny and restricted always-allow choices. Explicit page actions intentionally have different policy paths from AI. Capability availability is currently static rather than Linux-backend-derived; preserve user policy separately from actual platform support.

## Python worker audit

The Python worker is already registered through `PythonComputerBackend` → `HybridComputerBackend` → `ComputerActionExecutor` in App startup. README/module/XML comments claiming it is not integrated are stale. Existing backend supports a narrow Notepad editor and Chrome-owned Find field/scroll workflow; it excludes arbitrary web forms/address-bar input and generic click automation.

Private UTF-8 stdin/stdout NDJSON, one C# semaphore lane and worker queue, exact request fields, duplicate-key rejection, 8,192-character line limit, 100–15,000 ms timeout, bounded literal text/shortcut/scroll arguments, target identity pinning and redacted errors are reusable. Stderr is drained without retaining raw contents. The worker performs no AI planning or unrestricted shell/code evaluation. Existing app's input-enabled worker flag is nested beneath C# authorization; the flag alone is not authorization.

C# validates result ID/status/verified consistency and response length/depth, but not a complete strict response schema. No protocol version/capability handshake exists; arbitrary Data/unknown members are insufficiently constrained. Queue wait is caller-cancellable but outside request timeout. Malformed nonhashable action values can escape Python validation as TypeError in the reader; this is an untested robustness gap, not an execution bypass. Current mutations independently validate foreground/process/control identity and distinguish verified effects from possibly dispatched input. Native hangs still require parent kill. Cancellation/failure kills only the owned child and does not replay input. Focus dispatch accounting differs between Python and C# and should be normalized.

`windows.py` is intrinsically Windows UIA/ctypes/pywinauto. Reuse validator/dispatcher/lifecycle principles; retain this backend as legacy source and introduce a Linux adapter only in Phase 4. The health CLI can exit zero while returning a Failed JSON status: process exit alone is not a success test.

## Existing problems and technical debt

1. **Confirmed build blockers:** NETSDK1100 on Windows desktop targets; stale copied NuGet assets reference `C:\Program Files (x86)\Microsoft Visual Studio\Shared\NuGetPackages`. Fresh isolated Core restore/build succeeds. Enabling Windows targeting would only cross-compile a Windows artifact, not make WPF run on Ubuntu.
2. **Source risk: policy differs by caller.** ComputerCommandService checks local policy only for source `AI`; UI/Text callers can bypass those checks by design. A source string is not an authority boundary. Document explicit-user behavior and avoid accidentally reusing it for untrusted Linux entry points.
3. **Source risk: approval races.** Exact-command workspace path lacks router-style snapshot/final policy recheck; workspace changes during approval could alter execution. Router final check only rejects Denied/Unavailable, so an Allow→Ask transition during another approval can evade fresh confirmation. Generic app/workspace update tools have uneven target pinning. No exploit test performed.
4. **Source risk: destructive fallback on later save.** Corrupt/unsupported workspace stores load as empty without ProjectCatalog's read-only protection. Settings/policy/history also default on bad loads. Later save can overwrite recoverable files. Static `.tmp` names and no coordinated process locking complicate multiple app instances.
5. **Confirmed portability debt:** ignore-case physical identities, backslash directory-prefix filters, Windows aliases, HWND/UIA IDs and mixed logical/physical coordinates leak into shared code. Linux `A` and `a` can be different paths. Tiny monitor centering can produce an invalid clamp range (source risk, not reproduced).
6. **Confirmed worker protocol gaps:** strict request validation is stronger than response validation; no version handshake, queue deadline coverage or malformed-kind tests. Health exit code can mislead. Retain conservative input-uncertainty/no-replay semantics.
7. **Source risk: developer event provenance.** SID/session/peer PID checks restrict pipe peers but do not authenticate Claude/OpenCode executable identity. Same-user event tags are structured observations, not an OS audit. Preserve narrow approvals and explicit source confidence.
8. **Confirmed persistence/privacy limits:** no full conversation history, semantic code index, unrestricted terminal or automatic project watcher; local activity/log metadata may include paths/URLs/error details. Redaction is heuristic and not a proof that all secrets are removed.
9. **Confirmed UI debt:** much state/service invocation is code-behind; multi-tab Settings save is not transactional, and Cancel cannot undo prior explicit actions such as Test/Scan/key removal. Native STOP hooks and visibility state must not be dropped during MVVM extraction.
10. **Confirmed documentation drift:** README's no-input/no-Computer-Use statements and Python integration comments predate active native/Python action registration. Historical pass counts cannot establish today's Linux behavior. UI permission/onboarding copy also needs reconciliation during the UI phase.

## Reuse, replacement and test strategy

Retain algorithms/models, HTTP provider/error mapping, tool schemas/router/preparation, conversation/planning/context, policy definitions, workspace orchestration, metadata catalog, bounded project retrieval/search/redaction, developer normalization/supervision, actual result history and worker transport principles. Adapt their platform-shaped types, paths and test seams before claiming portability. Replace native WPF/WinForms/Win32/UIA/input/registry/credential/COM integrations with Linux providers; preserve the old source for later Windows work.

Existing tests are substantial (267 registered default C# cases by static enumeration; not executed here). Fakes cover provider streaming/tools/scoped credentials, policy, catalog ambiguity, workspace cancellation/partials, file privacy/encoding/links/budgets/injection, developer correlation/expiry/hooks, UI targeting/redaction, Computer Use STOP/visibility/takeover/verification and provider schema contracts. Windows live diagnostics are opt-in. The test project has no App reference, so navigation, WPF/Avalonia lifecycle, view lifetimes and native hooks lack automated presentation coverage.

Extract existing portable cases into a Linux-runnable harness before adding new frameworks. Native filesystem containment/case/link/race checks, Secret Service, XDG launch, peer authentication, real portal grants/revocation, takeover/focus and Avalonia startup/accessibility require real Ubuntu runtime tests.
